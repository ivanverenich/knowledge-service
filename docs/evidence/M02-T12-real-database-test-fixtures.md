# M02-T12 — Real-database test fixtures evidence

Completed: 2026-10-08

## Invariant

Every integration test starts from a migrated database that no other worker is
using: one pytest worker owns one database, so two workers running at the same
time never delete each other's rows. A test begins from an empty schema and
applies no migrations of its own. Nothing replaces SQL with a fake; the helpers
create, migrate, and drop real databases on a real server. The schema the
migrations produce and the tables the code declares are the same thing, and a
revision that drifts from the declared tables fails the suite instead of
silently diverging from it.

## Prediction

I expect the worker split to key the database name on the pytest worker id, so
`gw0` and `gw1` get separate databases and a run without workers uses the
configured one. `alembic check` should report no differences once
`synchronization_runs` and `sources` are declared, which they are not today, and
dropping a column from a migrated table should make it raise. The integration
files should stop reading the test URL themselves, the deterministic suite
should still pass without a database, and two concurrent workers should both
pass while leaving separate databases behind.

## Reflection

1. The fixture takes over three things a test author would otherwise have to
   remember every time: that the database must exist and be migrated, that it
   must be empty before the test's own inserts, and that a test which downgrades
   must not leave the schema broken for the next one. Forgetting the middle one
   produces a test that passes alone and fails in a suite; forgetting the last
   one produces a failure that looks like a bug in whichever test ran next.

2. One shared database with a rolled-back transaction per test is faster and
   needs no `CREATE DATABASE`, but it assumes every test keeps its work on one
   connection inside one transaction. That assumption is already false here: the
   transaction-ownership test reads from a second connection while the first is
   still publishing, and the migration test downgrades the schema and back. Both
   would break, and the second one would break in a way that leaks across tests
   rather than failing in place.

3. Without that assertion, the drift check could regress to a no-op — a
   `target_metadata` of `None`, a table declared but never created by any
   revision, a column renamed on one side only — and the suite would still be
   green. The failure would arrive with a deployment: a query against a column
   that the migrations never created, or a migration that silently skipped the
   change the code expects.
